Middleware / iPaaS vs native connector

A recurring design question: when should a connection run through Odoo's built-in providers and APIs, and when does it warrant a middleware layer (iPaaS such as an integration bus, queue, or low-code orchestrator)? The default is native; middleware is earned, not assumed.

Native connector — default

Use Odoo's own providers & APIs

MyInvois, payment providers, bank sync, mail gateway and Website/eCommerce all ship as maintained Odoo features. They version with the platform, need no extra hosting, and keep one source of truth. Custom AI reads/writes directly over XML-RPC/JSON-RPC.

Best when: a native provider exists, volume is modest, and the flow is point-to-point.

Middleware / iPaaS — when earned

Insert a broker only for real need

Justified when many systems fan-in/out, payloads need heavy transformation, retries and dead-letter queues must be guaranteed, or a partner system has no native Odoo link. Candidates: a managed iPaaS, a message queue, or the Odoo IoT Box for device traffic.

Cost: extra component to host, secure, monitor and license — only worth it past a clear complexity threshold.

IntegrationRecommended approachRationale
MyInvois, payments, bank, email, e-commerceNativeFirst-party Odoo support; no broker adds value
WhatsApp BusinessNative / BSPConnector or BSP webhook is sufficient at JR-Tech volume
IoT telemetryLight middlewareMQTT broker / IoT Box buffers and normalises device streams before Odoo
Custom AI servicesDirect RPCScoped API user over XML/JSON-RPC; add a queue only if batch volume grows
So what for the Odoo build: JR-Tech's launch architecture is deliberately broker-free — every Phase 1 integration is native. The only place middleware is pre-approved is IoT device traffic, and even that is deferred until predictive maintenance is on the roadmap. This keeps the go-live surface small, cheap to run and easy to audit.

Integration principles

Native first

Use built-ins before code

Payments, bank sync, email, e-commerce and MyInvois ship as Odoo providers/localisations. Configure these before building anything custom.

Event-driven

Webhooks over polling

WhatsApp and IoT push events to Odoo via webhooks/automated actions, avoiding brittle polling and keeping data fresh.

Secured

Scoped API access

External services authenticate with dedicated API users and the least-privilege roles defined on Security & Compliance.

So what for the Odoo build: the only must-have at go-live integrations are MyInvois, at least one MY payment method (FPX), bank reconciliation and email. WhatsApp and IoT/telemetry are sequenced into later phases on the roadmap, in step with the AI use-cases that depend on them in the AI catalog.
