Driver Incentive Scheme — chemical pail delivery, engineered for Odoo.

A performance-based monthly incentive for JR-Tech's 6 drivers across 3 lorries, built directly on the owner's v3 framework — pail-credit pools, a weighted KPI scorecard, leave and compliance gates — then hardened by TechNext into a fair, gameable-proof, fully parameterised model that a supervisor configures and runs inside Odoo 19.

What's the owner's, what's TechNext's. The pail-credit pool, the 40/50/5/5 KPI weights, the MC/EL leave gates, the 80% qualifier and the 3-band shape are all the owner's v3 design, kept intact. TechNext adds three configurable refinements — an achievable, genuinely-rewarded Excellent band; a humane leave-prorate option; and anti-gaming controls — each a switch the owner can turn on or off in Odoo settings without a developer.

1 · The pail-credit pool — what a driver can earn

Each driver has their own pool — no shared team pot, so one driver's weak month never dilutes another's. The pool is the maximum; the KPI score decides how much of it is actually paid.

Expert note — pool quantum. Real months land around RM50–RM200. That may be too small to shift behaviour. The RM rate is a single Odoo parameter, and an optional excellence bonus (below) adds real upside without rewriting the model.

2 · The KPI scorecard — how much of the pool is unlocked

Four components, two groups, weighted to 100%. Operations & compliance is half; hitting the actual delivery target is the other half — the single heaviest lever.

Weights are stored as Odoo parameters — the owner can re-balance (e.g. lift D.O. Return) without code.

Master formula

Total_KPI = att_score * 0.40 + job_pct * 0.50 + do_ret_pct * 0.05 + send_pct * 0.05 // each component on a 0–100 scale → result 0–100

Anti-gaming (TechNext). "Arranged" delivery counts must be set by the planner/route sheet, never by the driver being scored — otherwise a driver can lower their own target to inflate Job Completion. In Odoo this is enforced with record rules: drivers have read-only access to their KPI record.

3 · Gates & the 3-band payout

Gates are checked before the pool is paid, in a fixed order. This is the exact decision logic Odoo executes each month.

❌ Not Qualified

KPI < 80%, or leave gate tripped.
Payout = RM0.

🟡 Good

80% – <95%.
Payout = pool × KPI% (proportional).

🟢 Excellent

KPI ≥ 95% and D.O. Return ≥ 90% and Sending ≥ 80%.
Payout = full pool + bonus.

Flaw fixed — the Excellent band was empty. Under the raw v3 rules, Excellent required exactly 100% KPI, yet a 100% score already pays the full pool in the Good formula — so Excellent rewarded nothing and was near-impossible to reach. TechNext makes it reachable at a configurable 95% and attaches a real excellence bonus (default 10%) so top performance actually pays more.
Leave gate — two modes, you choose. Strict (owner default): MC > 2 days or EL > 1 day cancels the whole incentive. Prorate (TechNext-recommended for medical): the pool is scaled by attended working days instead of zeroed — fairer, lower morale/legal risk, still discourages abuse. A single leave_gate_mode setting switches between them.

5 · Configuring it in Odoo 19

The scheme is a small custom module, jrtech_driver_incentive, riding on standard HR / Inventory / Payroll. Every number above is a setting, not a code change — see the full build spec in Odoo 19 Architecture and the module doc in the repo (odoo/plan/driver-incentive-module.md).

Stands on

Employees (hr.employee), Attendance/Time Off (hr.attendance, hr.leave — custom MC & EL types), Inventory (stock.picking = Delivery Orders), Payroll (hr.payslip Other Input).

Custom models

jrtech.lorry · jrtech.trip.log · jrtech.attendance.daily · jrtech.driver.kpi.monthly (the core record, one per driver per month, all fields computed).

Runs itself

A monthly cron auto-creates KPI records; a WhatsApp webhook controller (/api/jrtech/trip_log) ingests trips; computed fields do the maths; payout posts to the payslip.

The payout as an Odoo computed field

def _compute_monthly_payout(self): for r in self: P = float(r.get_param) # settings cached # 1 · leave gate prorate = 1.0 if r.leave_gate_mode == 'strict' and (r.mc_days > P.mc_limit or r.el_days > P.el_limit): r.monthly_payout = 0.0; continue if r.leave_gate_mode == 'prorate': prorate = max(0.0, (r.working_days - r.mc_days - r.el_days) / r.working_days) # 2 · qualify threshold if r.total_kpi_pct < P.kpi_min_threshold: r.monthly_payout = 0.0; continue # 3 · band + payout pool = r.monthly_rm_pool if (r.total_kpi_pct >= P.excellent_kpi_threshold and r.do_return_pct >= P.do_return_gate and r.sending_pct >= P.sending_gate): r.rating = 'excellent' r.monthly_payout = pool * (1 + P.excellent_bonus_pct/100) * prorate else: r.rating = 'good' r.monthly_payout = pool * (r.total_kpi_pct/100) * prorate
Payroll posting. monthly_payout feeds the payslip as a separate Other Input line (rule code DRV_INC), keeping incentive visible and distinct from base salary, EPF/SOCSO handled per JR-Tech's payroll config.

Phased rollout

  1. Month 0 — parallel run. Configure module + settings; run Odoo alongside the current Excel for one month; reconcile to the cent.
  2. Month 1 — WhatsApp capture. Turn on the webhook; supervisor verifies 2 fields; payout still owner-approved.
  3. Month 2 — go live. Payout posts to payslip; driver self-dashboard enabled.
  4. Later — mobile app. Replace WhatsApp parsing with the Odoo mobile/PWA delivery log (same models).
Fairness & governance. Publish the rules to drivers up front; show the KPI breakdown on their dashboard so payout is never a black box; keep an audit trail on every KPI record; and review weights quarterly. A transparent scheme is what turns an incentive into behaviour change.
