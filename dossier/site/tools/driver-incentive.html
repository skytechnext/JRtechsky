Driver Incentive Scheme — a fair, gameable-proof
model that configures cleanly in Odoo.

Built from the owner's v3 handover spec and refined with compensation-design judgment. It keeps what works — per-driver pail-credit pools, a weighted KPI scorecard, monthly payout into payroll — and fixes the parts that quietly kill motivation: an unreachable "exactly 100%" top tier, a hard RM0 cliff, no safety dimension, and illness that zeroes a whole month. Every threshold, weight and gate is a Settings value in Odoo, so management tunes the scheme without a developer.

Design intent. Pay for output (pails moved), gate on quality & conduct (deliveries completed, DO signed, driving safe, showing up), keep the top tier reachable, protect genuine illness, and make every rule a knob — not a hard-coded constant. Volume sets the size of the reward; the KPI decides how much of it is earned.
Expert refinements

What we kept, and what we improved

The architecture is the owner's. These five changes are where a compensation lens earns its keep — each is optional and reversible via Settings, so you can run the exact v3 rules if you prefer.

Owner's v3 ruleWhy it hurts motivationRefined v4
EXCELLENT needs KPI = exactly 100% Practically unreachable (needs perfect attendance and 100% job completion and both gates). An unwinnable top prize is ignored. EXCELLENT at KPI ≥ 95% + gates. A real, earnable tier. Optional stretch bonus for a genuine clean 100% month. configurable
Hard cliff: KPI < 80% → RM0 A driver at 79% who moved hundreds of pails gets nothing → "give-up zone" and turnover risk. One rough month erases all effort. Keep the 80% full-scheme bar, but add an optional Developing band (60–79% → half-rate) so effort still pays while under-performance is still penalised. configurable · off = strict v3
No safety or conduct measure A driver incentive that ignores accidents, summonses, damage and complaints rewards speed over safety — the most expensive risk in the business. New Safety & Conduct component (10%) plus a serious-incident gate. new
MC > 2 or EL > 1 → whole incentive RM0 Genuine, documented illness shouldn't wipe out a month's earned pool — it reads as punishing sickness and invites presenteeism. Gate retained by default, but a "reduce, don't zero" option pro-rates for approved MC while still capping abuse. configurable
Attendance = 40% weight Showing up is table-stakes; at 40% it can outweigh actually completing deliveries. Rebalanced to 35%; the freed weight funds Safety. Delivery vs reliability stays a clean 50 / 50. configurable

Total KPI formula

# Each raw score is 0–100; weights are Settings values (must sum to 100) total_kpi = ( job_pct * 0.45 + do_pct * 0.05 + att_score * 0.35 + safety_pct * 0.10 + report_pct * 0.05 ) # → 0–100
To run the owner's exact v3: set weights to Job 50 · Att 40 · DO 5 · Report 5 · Safety 0, and turn the Safety gate off. One Settings change, no redeploy.

Component definitions

  • Job Completion = (chem + equip achieved) ÷ (chem + equip arranged). "Arranged" is locked by dispatch, never the driver.
  • Attendance = 100 − (late×10) − (unpaid-absent×20), floored at 0. MC/EL don't deduct (see gates).
  • Safety & Conduct = 100 − (minor events × penalty); a serious event trips the gate.
  • D.O. Return = signed-&-returned ÷ issued. Reporting = messages sent ÷ (delivery-days × 2), capped 100.
The reward pool

Pail credit — the size of the prize

Unchanged from the owner's design — it's sound. Each driver earns their own pool from their own trips; there is no shared team pool.

ScenarioCredit to this driverRM
Two drivers on the lorrypails ÷ 2credit × rate
Solo (partner absent)full pailscredit × rate
# per trip pail_credit = pails / 2 if partner_present else pails rm_value = pail_credit * pail_rm_rate # rate = Settings (default RM1) # monthly pool monthly_pool = SUM(rm_value) where driver = self and month = period

Two optional upgrades

  • Per-product rate — a heavier or hazardous chemical can carry a higher RM/pail than a light one, via a rate on the product. Defaults to the flat RM1 for everyone.
  • Distance / zone factor — an optional multiplier for long-haul rural drops so remote routes aren't penalised for lower pail counts. Off by default.
Anti-gaming guardrails. "Arranged" is set by dispatch and locked; the supervisor must tick Verified on each trip before its credit counts; and a monthly reasonableness cap flags any pool > a configurable ceiling for review.
Payout

Four tiers, no cliff

< 60%
Payout = RM0

60–79%

Off by default (= strict v3, where <80% is RM0). On = effort still pays, at half rate.

🟡 QUALIFIED

80–94%
Pool × KPI%
e.g. 88% KPI on an RM200 pool → RM176.

🟢 EXCELLENT

≥ 95%
Full pool (100%)
Needs DO ≥ 90%, Reporting ≥ 80%, no safety incident. Optional stretch bonus at a clean 100%.

Decision order (implement exactly like this)

  1. Verify & gate — leave. If MC > limit or EL > limit → default RM0 (or pro-rate if "reduce, don't zero" is on).
  2. Gate — safety. A serious incident this month (at-fault accident, major summons, verified serious complaint) → RM0, routed to management review.
  3. Compute KPI from the five weighted components.
  4. Below qualifying floor? KPI < 60% → RM0. Between the floor and 80% → Developing band (if enabled), else RM0.
  5. Qualified? 80–94% → Pool × KPI%.
  6. Excellent? KPI ≥ 95% AND DO ≥ 90% AND Reporting ≥ 80% AND no incident → full pool (+ optional stretch).

Payout function (Odoo computed field)

def _compute_payout(self): p = self.monthly_pool # 1 · leave gate if self.mc_days > self.cfg_mc_limit or self.el_days > self.cfg_el_limit: self.payout = p * self.leave_prorata if self.cfg_leave_reduce else 0; return # 2 · safety gate if self.serious_incident: self.payout = 0; return k = self.total_kpi # 0–100 # 3 · floors & bands if k < self.cfg_dev_floor: self.payout = 0 elif k < self.cfg_qualify: self.payout = p * (k/100) * self.cfg_dev_rate if self.cfg_dev_on else 0 elif k < self.cfg_excellent: self.payout = p * (k/100) elif self.do_pct >= self.cfg_do_gate and self.report_pct >= self.cfg_report_gate: bonus = self.cfg_stretch if k >= 100 else 0 self.payout = p * (1 + bonus) # EXCELLENT (+ stretch) else: self.payout = p * (k/100)

Odoo blueprint

Configure it in Odoo — standard modules first, thin custom on top

Reuse what Odoo already does well (employees, attendance, time off, deliveries, fleet, payroll) and add one small module for the incentive maths. Nothing operational is hard-coded — the numbers all live on a Settings page.

hr
Employees, Attendance, Time Off — drivers, lates, MC/EL
stock
Delivery Orders = pickings; DO signed-return flag
fleet
Lorries as fleet.vehicle; safety events per vehicle/driver
payroll
Payout as a payslip "Other Input" line

Custom module jrtech_driver_incentive

Models

  • jrtech.trip.log — one row per delivery trip: date, vehicle_id (fleet), driver_1_id/driver_2_id (hr.employee), customer_id, pails, verified; computes pail credit & RM per driver.
  • jrtech.safety.event — date, driver, severity (minor / serious), type (accident / summons / damage / complaint), notes. Feeds the Safety score & gate.
  • jrtech.driver.kpi.monthly — the core object: one per driver per month, all computed scores, rating & payout. Auto-created by cron on the 1st.

Standard-Odoo mappings

  • DOs → stock.picking + boolean x_do_signed_returned; monthly counts via read_group.
  • Lates → hr.attendance check-in vs shift start; MC/EL → two hr.leave.types, counted from hr.leave.
  • Payout → salary rule reading the KPI record's payout as an Other Input on the payslip.

Build order

  1. Master data — drivers in Employees, lorries in Fleet, custom MC/EL leave types, shift start time.
  2. Trip & safety capture — Trip Log (WhatsApp webhook /api/jrtech/trip interim → later the app) and Safety Event models + supervisor "Verified" step.
  3. Settings page — expose every parameter above; seed the defaults.
  4. Monthly KPI object — computed scores, gates, rating and payout; cron auto-creates records on the 1st.
  5. Payroll link — salary rule maps payout to a payslip Other Input.
  6. Views & access — supervisor entry, manager pivot (6 drivers × 12 months), and a read-only driver self-service view so each driver sees their own KPI and payout — transparency drives the behaviour.
Rollout. Run one month in parallel with the current Excel to validate the numbers against the worked examples, brief the drivers on the rules and the self-service view, then switch over and review the thresholds after three months.
